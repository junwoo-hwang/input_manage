# input_manage — 기준 정보 관리

SF GDVC 포털의 메뉴 하나. S3 drive 에 있는 기준 정보 엑셀을 **브라우저에서
엑셀처럼 고치고 바로 저장**한다. 내려받았다 고쳐서 다시 올리는 왕복이 없다.

```
G-DVC / 2GAPU/input /
    FAB_INPUT_ULY_r0.xlsx     <- 이 폴더의 .xlsx 가 곧 편집 대상 목록
    FAB_INPUT_TTS_r0.xlsx
    이력 /
        260921_FAB_INPUT_ULY_r0_junwoo.hwang.xlsx    <- 저장할 때마다 한 벌
        260921_FAB_INPUT_ULY_r0_junwoo.hwang_2.xlsx  <- 같은 날 또 저장하면
```

**누가 언제 무엇을 바꿨는지**는 그 엑셀 안의 `REV_INFO` 시트에 한 줄씩
쌓인다 — 기준 정보를 받아 보는 사람이 파일 하나만 열면 이력까지 같이
보는 것이 맞다. 옆에 감사용 파일을 따로 두면 그 둘이 갈리기 시작한다.

**되돌릴 사본**은 다른 얘기라 `이력/` 폴더에 쌓는다. 저장할 때마다
`{YYMMDD}_{파일이름}_{사번}.xlsx` 로 한 벌 넣는다. 날짜가 앞에 오므로 폴더를
이름순으로 보면 그대로 시간순이다. 같은 사람이 같은 날 또
저장하면 이름이 겹치는데, 그대로 두면 앞의 판이 조용히 덮어써지므로 뒤에
번호를 붙인다. **사본을 못 남기면 본 파일도 안 건드린다** — 그 순서로
넣었다.

폴더 이름은 `INPUT_S3_HISTORY_DIR` 로 바꿀 수 있다 (기본 `이력`).
지우는 코드는 없다. 쌓이는 속도는 저장 횟수만큼이고, 너무 늘면 사람이
지우면 된다.

## 되는 것

- 위 드롭다운에서 파일을 고르면 그 엑셀이 통째로 뜬다 (시트는 표 아래 탭)
- **이름 상자 + 수식 입력줄** — 주소는 `A1`, `E1493` 엑셀 표기이고 거기서
  값을 바로 고칠 수 있다
- 셀을 **끌어서 범위 선택**, 열 머리글로 열 전체 선택
- **오른쪽 클릭 차림표** — 잘라내기 / 복사 / 붙여넣기 / 행·열 넣고 빼기 /
  내용 지우기
- **복사 / 붙여넣기가 엑셀과 오간다** (클립보드 TSV)
- **행 / 열 추가·삭제**, 열 이름 바꾸기(머리글 더블클릭)
- **찾기** (Ctrl+F) — 몇 개 중 몇 번째인지 세어 주고 그 칸으로 데려간다
- 되돌리기 / 다시 (Ctrl+Z / Ctrl+Y)
- **엑셀 다운로드** — S3 에 저장돼 있는 그 파일을 그대로 받는다 (아직 저장
  안 한 화면의 수정은 안 들어간다)
- **엑셀 업로드** — 많은 줄을 한 번에 바꿀 때. 내려받아 엑셀에서 고친 파일을
  올리면 그 내용이 화면에 들어온다. **올리는 것만으로는 저장되지 않는다** —
  손으로 고친 것과 똑같이 저장을 눌러야 하고, 무엇이 바뀌는지도 똑같이
  `변경내용` 창에 뜨고 `REV_INFO` 에 남는다
- **저장하기 전에 `변경내용` 창이 뜬다** — 어느 시트(`sheet : STEP`)의 몇째
  줄이 `신규` / `수정` / `삭제` 인지 줄 전체를 펼쳐서
- `REV_INFO` 시트가 있으면 **사유(`Remark`)를 적어야 저장된다**. `Date`(한국
  시간)와 `user`(로그인한 사람)는 자동으로 박히고 고칠 수 없다 —
  언제 누가 바꿨는지는 기록이지 입력이 아니다. `관련` 은 안 적어도 된다
- 그 창은 **Esc 로 닫히지 않는다** — 적던 사유가 통째로 날아가기 때문이다.
  닫으려면 `취소` 나 오른쪽 위 X 다
- 창에서 저장을 누르면 **그 자리에서 단추가 `저장 중…` 회색으로 꺼진다**. 저장이
  도는 몇 초 동안 켜져 있으면 한 번 더 누르게 되기 때문이다. 그래서 누른 판에서는
  '눌렀다' 만 적고 곧바로 다시 그리고(단추가 꺼진 채로), 저장은 그다음 판에서
  한 번만 한다. 빠르게 두 번 눌러도 한 번 저장된다. 저장이 실패하면 창이 다시
  켜지고 까닭이 뜬다 (적어 둔 사유는 그대로)
- **`변경 이력`** 을 펼치면 그 `REV_INFO` 시트를 최근 것부터 보여준다
- 저장하면 S3 의 그 엑셀이 바로 바뀌고, **창에서 본 변경내용이 그대로**
  `REV_INFO` 의 `관련` 칸에 들어간다 (사람이 적은 것 먼저, 그 아래에)
- 같은 값으로 **`이력/` 폴더에 사본 한 벌**이 들어간다 (되돌릴 때 쓴다)
- 저장이 끝나면 **`저장 완료!` 창**이 뜬다 (확인·X·Esc 로 닫는다)

### 수식 (`VLOOKUP` 같은 것)

화면에는 **마지막으로 계산된 값**이 보이고, 저장할 때 **수식 그대로** 다시
쓴다. 파일을 열 때 엑셀이 다시 계산하도록도 적어 둔다(`fullCalcOnLoad`).

다만 수식은 제가 앉은 자리를 기준으로 옆 칸을 가리킨다 — 5번 줄의
`=VLOOKUP(B5,...)` 는 6번 줄로 밀리면 `B6` 을 봐야 맞다. 엑셀은 줄을 끼워
넣을 때 그걸 알아서 고쳐 주지만 우리는 못 한다. 그래서 **줄이 제자리에 있을
때만** 수식을 지키고, 위에 줄이 끼거나 빠져서 밀린 줄의 수식은 버린다
(마지막 계산값으로 굳는다). 몇 개를 버리는지는 저장 전에 `변경내용` 창이
알려 주니, 수식을 지켜야 하면 취소하고 줄 넣고 빼는 것은 엑셀에서 하면 된다.

그 칸에 사람이 직접 값을 적었으면 사람이 적은 값이 이긴다.

**정확매칭 VLOOKUP(마지막 인자가 0 또는 FALSE)은 저장할 때 우리가 대신
계산해서 캐시 값을 맞춘다.** `=VLOOKUP(E10220,ET추출여부!$A:$C,3,0)` 같은
꼴이다. 이게 왜 필요하냐면: 우리는 엑셀이 아니라 수식을 계산하지 않는다.
그래서 A 시트를 고쳐 B 시트의 VLOOKUP 이 다른 값을 가리키게 됐어도, 저장한
파일 안의 캐시 값은 고치기 전 값 그대로다. **엑셀로 열면** 열자마자
다시 계산해서 맞아지지만, **이 파일을 pandas 등으로 직접 읽는 파이프라인은
엑셀을 안 거치므로 낡은 값을 그대로 가져간다.** 그래서 저장 시점에 우리가
직접 계산해 캐시를 맞춰 둔다.

찾아볼 표는 **한 번만 뒤집어 놓고** 수식들이 나눠 쓴다. 수식마다 그 표를
처음부터 훑으면 수식 개수 x 표 줄수가 되는데, 줄마다 VLOOKUP 이 걸린 시트
에서는 그게 곧 저장이 분 단위로 걸린다는 뜻이다 (수식 4,000개 x 표 5,000줄
이 5.3초, 15,000개면 그 몇 배). 지금은 같은 일이 0.26초다.

근사매칭(마지막 인자가 없거나 TRUE)이나 VLOOKUP 이 아닌 다른 함수는 계산
하지 않는다 — 계산을 잘못하면 조용히 틀린 값을 주는 것이라 안 하느니만
못하다. 그런 칸은 지금까지와 같이 낡은 채로 남는다(수식 자체는 살아 있어
엑셀로 열면 맞는다).

### 안 되는 것

- **글꼴·색·굵게 같은 서식**은 없다. 값만 다룬다. 서식 단추를 달아 봐야
  저장되지 않아 다시 열면 사라지므로, 없는 편이 덜 헷갈린다.
- 셀 병합, 틀 고정, 차트, 조건부 서식.

2번 구역이다.

읽을 때 감당하는 것: 엑셀 본프로그램이 쓰는 sharedStrings, openpyxl 이 쓰는
inlineStr, 수식 칸(마지막 계산값), 날짜(엑셀은 날짜를 수로 저장하고 서식으로만
구분한다), 참/거짓, 중간이 비어 건너뛴 칸과 줄. 쓸 때는 엑셀처럼 sharedStrings
로 쓴다.

직접 만든 것이라 '엑셀이 진짜로 읽고 쓰는 꼴' 과 맞는지는 남이 봐 줘야 한다.
`tests/test_xlsx.py` 가 그걸 openpyxl 에 맡긴다 — 개발 환경에만 깔고
(`requirements-dev.txt`) 양쪽으로 맞춰 본다. 돌아가는 코드는 안 쓴다.

## 실제 크기에서

기준으로 삼은 파일: 16,000줄 2장, 8,000줄 1장, 6,000줄 2장, 칸 28개씩(모두 146만
칸), 줄마다 VLOOKUP 두 개(수식 32,000개), 8MB. 처음에 15,000줄 x 6칸으로만
재고 맞춰 두었다가, 칸이 28개가 되니 딴판이었다 -- 칸 수만큼 곱해지는 것들이
숨어 있었다. 아래는 이 파일로 잰 것이다 (S3 왕복은 빼고, 이 서버 안에서).

| | 지금 | 고치기 전 |
|---|---|---|
| **처음 열기: 첫 줄이 보이기까지** | **4.9초** | 8.0초 |
| 같은 판을 또 열 때 엑셀 읽기 | **0초** (한 번 읽은 것을 나눠 씀) | 매번 8.6초 |
| 마지막 줄까지 다 붙기 | 7.7초 | 9.4초 |
| **칸 하나 고치기** | **0.16초** | 0.5초 |
| 한 번에 멈추는 가장 긴 시간 | 0.24초 | 0.79초 |
| 시트 바꾸기 (16,000줄) | 1.0초 (첫 화면) | 3.1초 |
| **저장 -> 변경내용 창** | **2.1초** | 7.7초 (창 안의 셈만 12초) |
| 창에서 저장 -> 저장 끝 | 2.6초 | 2.3초 + 도로 읽기 6초 |
| 칸을 고칠수록 브라우저 메모리 | 그대로 | 칸 하나에 6MB 씩 |
| 수식 32,000개 캐시 다시 계산 | 0.12초 | (분 단위) |

줄은 **전부** 그린다. 보이는 만큼만 그리면 브라우저 Ctrl+F 가 값을 못 찾고,
스크롤 막대가 실제 줄과 어긋나 보인다 -- 눈으로 훑어 찾는 표라 그게 더 나쁘다.
대신 여러 가지로 값을 치른다.

### 브라우저 쪽

**하나. 표를 `<table>` 이 아니라 `<div>` 로 그리고, 50줄씩 묶는다.** 보기에는
같다. CSS 의 크기 가둠(containment)이 표의 행에는 적용되지 않게 정해져 있어서,
`<tr>` 에는 `content-visibility` 를 줘도 브라우저가 배치를 건너뛰지 못한다.
`<div>` 면 건너뛴다 -- 15,000줄을 그리고 높이를 재는 데 4,794ms 대 83ms 다.

건너뛰는 단위는 줄이 아니라 50줄 묶음(`.blk`)이다. 브라우저는 건너뛰는 덩이
마다 '지금 화면에 들어왔나' 를 매 그림마다 따지는데, 16,000줄을 줄마다 따지면
칸 하나 고치는 동안 그게 여러 번 돌아 한 번에 0.45초였다. 묶으면 따질 것이
320개라 0.17초다. (25줄, 200줄로도 재 봤는데 50줄이 가장 빨랐다.)

여기서 조심할 것: 묶음이 미리 알려 주는 높이(50줄 x 25px = 1250px)가 실제와
같아야 한다. 다르면 스크롤 막대 길이가 틀어진다. `padding` 하나만 건드려도
어긋나므로 검사로 묶어 뒀다. 시트 끝의 모자란 묶음은 그 자리에서 제 높이를
적는다.

**둘. 첫 화면을 먼저 내놓고 나머지를 이어 붙인다.** 300줄만 먼저 내놓고
나머지는 칸 18,000개 분량씩 덧붙인다. 줄 수로 끊던 때(3,000줄씩)는 6칸짜리
에서는 괜찮았지만 28칸짜리에서는 한 덩이가 8만 칸이라 0.7초씩 멈췄다. 아직 안
그린 만큼은 빈 자리로 미리 잡아 둬서 스크롤 막대가 처음부터 맞는다.

**셋. 값이 바뀌면 그 칸 하나만, 고른 자리가 바뀌면 칠한 사각형 두 개만
손본다.** 칸은 선택자로 찾지 않고 '몇 번째 묶음의 몇 번째 줄의 몇 번째 칸'
으로 바로 집는다. 선택자(`.cell[data-r=..][data-c=..]`)로 찾으면 브라우저가
45만 칸을 처음부터 훑는다.

**넷. 되돌리기 판은 줄을 나눠 쓴다.** 예전에는 칸 하나 고칠 때마다 모든 시트의
모든 칸(146만)을 복사해 60판까지 들고 있었다. 지금은 줄 목록만 복사하고, 줄을
고칠 때는 그 줄만 복사해 갈아 끼운다. 그래서 줄(배열)을 그 자리에서 고치면
안 된다 -- 지난 판까지 같이 바뀐다. 검사로 묶어 뒀다.

### 격자와 파이썬 사이

**다섯. 편집 중에는 파이썬을 거의 안 깨운다.** 처음 한 번만 '고친 게 있다' 를
알린다. 한 번 참이 되면 저장하거나 초기화할 때까지 계속 참이라 또 알릴 것이
없다. 칸마다 알리면 그때마다 streamlit 이 스크립트를 다시 돌려서 고칠 때마다
화면에 로딩이 번쩍인다.

**여섯. 표는 격자가 그 판을 안 가졌을 때만 내려보낸다.** streamlit 은
컴포넌트에 넘기는 값이 하나라도 바뀌면 전부를 다시 보낸다. 저장을 누르면
'표를 달라' 는 표시(`want_full`)가 바뀌어서, 그때마다 14MB 가 다시 내려갔다.
이제 격자는 올려보낼 때마다 자기가 가진 판(`have`)을 알리고, 파이썬은 그 판이면
표를 빼고 보낸다. 격자 틀이 새로 만들어져 표를 잃으면 격자가 '없다' 고 알려
다음 판에 다시 받는다.

**일곱. 표는 시트마다 JSON 글자 하나로, 판마다 한 번만 만든다.** 줄과 칸을
그대로 넘기면 브라우저가 146만 개의 글자를 하나씩 만들고, 격자 틀로 옮길 때 또
하나씩 복사한다. 글자 하나면 옮기는 것은 한 번의 복사이고, 격자는 지금 보는
시트만 푼다(0.05초). 나머지는 그 시트를 처음 열 때 푼다.

**여덟. 저장할 때는 손댄 시트만 올린다.** 손대지 않은 시트는 이름과 '원래
이것' 만 올리고, 파이썬은 내려보냈던 그 표를 그대로 쓴다. 같은 표 객체라서
'무엇이 바뀌었나' 와 '살아남는 수식' 도 그 시트는 보지도 않고 건너뛴다.

**아홉. 저장 창에서도 안 깨운다.** 사유를 적는 칸은 `st.form` 으로 묶었다.
안 묶으면 칸을 떠날 때마다 스크립트를 처음부터 다시 돈다. 바뀌지 않는 셈(무엇이
바뀌었나, 어느 수식이 살아남나)은 창을 띄울 때 한 번만 하고 들고 있는다.

묶은 이유가 하나 더 있다. 칸에 적은 값은 칸을 떠나야 파이썬에 닿는데, 사람은
적자마자 저장을 누른다 -- 그 누름이 '칸을 떠났다' 로 먼저 처리되면서, 그 판에서
저장 단추는 아직 사유가 빈 줄 알고 꺼져 있었다. **한 번 눌러서는 저장이 안 되고
두 번 눌러야 했다.** form 안에서는 누름 한 번에 칸 값이 같이 실려 온다.

### 파이썬 쪽

**열. 같은 판(ETag)은 서버 안에서 한 번만 읽는다.** 여럿이 같은 파일을 열 때,
파일을 바꿔 골랐다 돌아올 때, 아무도 저장 안 했는데 초기화를 누를 때 -- 전부
같은 판이다. HEAD 로 ETag 만 물어보고 가진 판이면 내려받지도 않는다. 누가
저장하면 ETag 가 바뀌어 새로 읽는다. 나눠 쓰는 표라 고치면 안 된다 (고칠 때는
늘 새 표를 만든다).

**열하나. 큰 표를 다루는 동안 GC 를 잠시 멈춘다.** 8MB 엑셀을 읽으면 XML 칸
객체가 300만 개 가까이 생기는데, 그 사이 파이썬 GC 가 수십 번 깨어나 지금까지
만든 것 전부를 훑느라 읽는 시간의 절반 이상을 썼다(7.2초 중 4초). 멈추면 같은
파서로 3.3초다. 메모리가 새지는 않는다 -- 대부분은 참조 수로 바로 치워지고, 다시
켜면 남은 고리도 치운다. 여럿이 동시에 들어와도 마지막 사람이 나갈 때 켠다.

**열둘. 칸 하나씩 pandas 로 꺼내지 않는다.** `.iloc`, `.at`, `itertuples` 는
한 번에 수십 마이크로초다(pandas 3 은 글자를 Arrow 로 들고 있어 더하다). 칸
수(146만)나 수식 수(32,000)만큼 돌면 그것만 10초였다. 값 배열로 한 번 꺼내 쓴다.

**열셋. 엑셀을 쓸 때 글자를 sharedStrings 로 모은다** (엑셀이 쓰는 방식). 칸마다
글자를 넣던 때보다 XML 이 줄어서 쓰기도, 나중에 다시 읽기도 빠르고(10.3초 ->
2.4초), 파일도 7.9MB 에서 7.0MB 로 준다.

**열넷. 저장한 뒤 S3 에서 도로 안 읽는다.** 방금 올린 바이트가 곧 지금 S3 에
있는 바이트다.

'엑셀 다운로드' 는 표를 받아올 필요가 없다 — S3 에서 받아 들고 있는 바이트를
그대로 내주므로 누르면 바로 받아진다.

## 왜 st.data_editor 가 아닌가

`st.data_editor` 는 **열을 못 넣고 못 뺀다.** 칸 구성이 DataFrame 스키마로
고정돼서, 기준 정보에 칸 하나 추가하려면 결국 엑셀을 내려받아 고쳐 다시
올려야 한다 — 그게 하기 싫어서 만든 화면이라 그걸로는 끝이 안 난다.

그래서 격자를 직접 만들었다. `frontend/index.html` 하나이고 npm 빌드 단계가
없다. iframe 과 부모 사이의 postMessage 규약 세 가지(componentReady /
render / setComponentValue)만 직접 지킨다.
